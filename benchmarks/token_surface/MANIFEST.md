# token_surface benchmark — MANIFEST

Falsifiable token-efficiency evidence for the issue #56 token surface (ids-only
detail mode + tabular output). Reproducible: the fixture is generated in-code, so
`cargo run -p token-surface-bench --release` regenerates `results.json`.

## Provenance
- **Base commit:** `37a55fe` (branch `feat/token-surface-56` off this).
- **Date:** 2026-07-25.
- **Toolchain:** rustc 1.95.0, release profile.
- **Search/graph dependency set (issue #78):** tantivy 0.26.1, lbug 0.18.3.
  Re-run after the upgrade from tantivy 0.22.1 / lbug 0.15.4. A search-engine
  change can move ranking silently, so these numbers are not carried over from
  the previous versions; they were regenerated on this dependency set.
- **Command:** `cargo run -p token-surface-bench --release` → writes `results.json`.

## Methodology
- **Fixture:** a generated Python repo — `core.py` (defines `core_process` +
  `Config` + `load_config`), `main.py`, and 40 module files that each call
  `core_process` and reference `Config`. Deterministic, so numbers are stable
  across runs on the same code.
- **Real pipeline, real renderer:** the benchmark drives the actual library —
  `indexer::index_codebase_with_language` → `resolver::resolve_graph` →
  `clustering::cluster_graph` — and shapes results through the SAME
  `token_surface::render_list` the MCP tools use. It is not a re-implementation
  of the tool output; the object shapes mirror the handlers'.
- **Fixed 5-query structural workload** (the questions an agent asks a code
  graph): (Q1) search functions matching "process", (Q2) list every function's
  qualified name, (Q3) list all execution processes, (Q4) who depends on
  `core_process`, (Q5) search symbols matching "config".
- **Token proxy:** characters of compact JSON serialization. ~4 chars ≈ 1 token
  (stated as an approximation; the reduction *ratio* is proxy-independent). Each
  query's response is serialized with a representative envelope (tool, counts,
  offset) held identical across encodings, so the measured delta is purely the
  list encoding — a conservative, realistic measure (the envelope dilutes the
  ratio rather than inflating it).

## Two comparisons
### (a) ids/tabular vs current JSON — the issue's ≥30% criterion
Same queries, three encodings summed over the 5:
- current JSON (array of objects): **26,756 chars**
- tabular (columns-once + row arrays): **13,900 chars → 48.0% reduction**
- ids (bare identifiers): **5,068 chars → 81.1% reduction**

Both compact modes clear the ≥30% bar; tabular is the apples-to-apples
"same information, fewer tokens" comparison, ids is the cheapest wide sweep.

### (b) graph tools vs a scripted grep/read transcript — marketing ratio
- graph (tabular) total: **13,900 chars**
- grep/read transcript: **23,508 chars → files/graph ≈ 1.7×**

**Honesty caveat:** comparison (b) is a **scripted simulation** of what a
file-exploring agent would consume (grep `path:line:text` output for each
question's keyword + full contents of the files that hold the answer, deduped
across questions), **not a live agent run**. The 1.7× is on a 42-file fixture; it
grows with repository size — a real repo has thousands of files a grep/read sweep
would page through, while the graph answer stays bounded and paginated. Reported
separately from (a) precisely because it is directional evidence, not the
acceptance metric.
